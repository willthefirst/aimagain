# Posts templates

Jinja templates for the post CRUD flows. HTMX-driven; forms submit form-encoded data via `hx-{post,patch}` (see [`_client_referral_form.html`](_client_referral_form.html) / [`_provider_availability_form.html`](_provider_availability_form.html)). Multi-checkbox fields (`desired_times`, `services`, `settings`) are normalized on the wire schema by `_scalar_to_list` in [`src/domain/logic/posts/schema.py`](../../logic/posts/schema.py).

## Files

- `list.html` — listing page (`GET /posts`). Renders a `<section id="posts-list">` via the `post_item` macro in `_item.html` — one `<article>` card per post. Each card has Pico's default `<article>` framing; the macro adds a 4px left edge in the kind color (orange = Seeking, cyan = Providing) for peripheral-vision differentiation. The toolbar (rendered by `views/list.html` → `_shared/_toolbar.html::page_toolbar`) right-aligns the filter link and a "Create post" `<a role="button">` (linking to `/posts/form` (no `?kind=`), which renders the kind picker). The filter link reads "Filters" when none are applied; with filters active it summarizes them inline ("Type: Seeking, Description: needle, +1 more filter") and opens `/posts/search`, where the form's own "Clear" button owns clearing. Every filter control — `?kind=` (Seeking / Providing), `?q=`, `?posted_by=`, `?state=`, `?city=`, `?age_group=`, `?language=` — lives on `/posts/search` (rendered by `views/search.html`). `?kind=` is rejected with 422 on unknown via `ChoiceFilter.value_type=Literal[...]`. Filters left out today: `created_at` (waits on a `DateRangeFilter` type) and `insurance` (vocab asymmetric across kinds — needs a unified posture mapping). The `#posts-list > article` selector wraps each card; each carries `data-row-id` and `data-kind` for tests.
- `search.html` — the dedicated filter page (`GET /posts/search`). One-line stub that extends `views/search.html` and sets the `Posts` breadcrumb label; every form control is driven by `POST_ENTITY.declared_filters`. Submits via GET back to `/posts`; the search page never owns applied state — it constructs a URL the list page reads.
- `_item.html` — `post_item(post, active_kind=None)`. Renders a card-shaped `<article>` per post. **Header line:** `<strong><a>{headline}, {state}</a> ({format-summary})</strong>` plus a right-aligned `<small>` with the date. The headline varies by kind: `Client Referral` for CR (no client name available; the kind label fills the identity slot) and `{practice_name}` for PA (the practice IS the identity). The `(format-summary)` parenthetical collapses the in-person/virtual posture into `(virtual or in person)` / `(in person)` / `(virtual)` / `(contact for format)`, or is omitted if neither arm is `yes`. **Body:** a three-column CSS grid (collapses to one column under 640px):
  - **Seeking / Providing** (left) — `<h4>` is kind-aware (`Seeking` for `client_referral`, `Providing` for `provider_availability`, reusing the chip vocabulary documented for the colored left edge below) + `<ul>` of services. Each `<li>` carries a Lucide icon next to the service label. Service order is priority-sorted, not enum-order: `psychotherapy` and `medication_management` lead the list — the two services a reader is overwhelmingly likeliest to be scanning for — and the rest follow in `CLIENT_REFERRAL_SERVICES` declaration order. For PA the list also includes `settings` (outpatient / IOP / PHP / etc.) under the same heading, unsorted, since the reader doesn't care about the schema-level split at scan distance. Omitted if the post has neither services nor settings.
  - **Demographics** (middle) — `<dl>` of `Label: value` chunks. Labels in scope: **Age**, **Languages** (when non-English), **Insurance** (unified posture, see below), **Modality** (when `treatment_modality` is set). Labels are visible `<dt>` elements; the `:` separator is added by CSS `dt::after`.
  - **Contact** (right) — `<h4>Contact</h4>` + the *name* of who you're reaching + a `mailto:` link as the action. Name varies by kind: `@{username}` for `client_referral` (the User account is the only identity available for the referring provider) and `{practice_name}` for `provider_availability` (the practice IS the provider). The email link carries `target="_blank" rel="noopener noreferrer"` — harmless on `mailto:` URLs and matches the pattern used for the PA website link on the detail page.

  The `<article>` carries `data-kind` and the card has a 4px left edge in the kind color (orange = Seeking, cyan = Providing) — peripheral-vision differentiator, replacing the earlier inline `[data-kind-chip]` text chip. **Insurance posture** is the unified 4-state derived value from [`../../logic/posts/view.py`](../../logic/posts/view.py)`::insurance_posture_for_post`, exposed as the `insurance_posture` Jinja global — collapses the asymmetric CR (`insurance` enum) and PA (Provider's `accepts_in_network` / `accepts_out_of_network` / `sliding_scale` flags) into one labeled chunk in the demographics column. The Lucide icon font is loaded by [`../../../framework/templates/base.html`](../../../framework/templates/base.html); per-enum `*_ICONS` dicts in [`../../models/enums.py`](../../models/enums.py) drive the service-icon mapping. The description prose does NOT appear in the row — it lives on the detail page where the reader has committed to reading. `active_kind` is accepted for backward compatibility with the `list.html` caller but is no longer consulted — the left-edge color is constant per-kind, so a single-kind filter doesn't need to suppress anything.
- `detail.html` — single-post read view (`GET /posts/{id}`). The *unfold* of a listing row: sections are ordered by what a reader needs to decide whether to act. (1) `<header><hgroup>` echoes the row's chip + a kind-appropriate title (synthesized `"Seeking in <city>, <state>"` for client_referral; `practice_name` for provider_availability). (2) Description prose, promoted above the metadata grid. (3) Match-facts `<dl>` — the row's meta-line tokens expanded into full lists (every age group, every language, every in-network carrier, schedule_text, treatment modality, sliding scale, cost). (4) Call-to-action `<section>How to refer</section>` for `provider_availability` carrying website + referral instructions. Posted-at uses the same `format_post_date` filter as the list. Includes `_owner_actions.html` in the footer.
- `_client_referral_form.html` / `_provider_availability_form.html` — per-kind form-body macros. Each takes `(hx_method, action, submit_label, post=None)` and renders the full intake form using the shared field-render macros from [`../_shared/form_fields.html`](../_shared/form_fields.html). Field order, section grouping, labels, and required/optional state live here in one place per kind.
- `new_<kind>.html` — create-form page; ~5-line wrapper that imports the per-kind form macro and calls it with `hx_method="post"`, `action="/posts"`.
- `edit_<kind>.html` — edit-form page; same wrapper pattern with `hx_method="patch"`, `action="/posts/{id}"`, and `post=post` for prefill.
- `_owner_actions.html` — partial showing Edit/Delete actions for owners and admins; kind-agnostic.

## Parent / per-kind detail

`Post` is split into a parent row (id, kind, owner, timestamps) and a per-kind detail row. Kinds today: `client_referral` (`post.client_referral_detail`) and `provider_availability` (`post.provider_availability_detail`). Both carry the scalar (single-value) fields from their intake forms plus the `desired_times` (7×3 grid) and `services` (5-checkbox) multi-selects, both stored as JSON. CR's `services` is optional; PA's is required-min-1. PA also carries the `settings` (5-checkbox) multi-select (required-min-1).

Templates dereference through the right relationship per branch: `{{ d.description }}` after `{% set d = post.client_referral_detail %}` inside a `kind == "client_referral"` block, etc. Don't reach for `post.title` — it isn't there. Detail relationships are eager-loaded (`lazy="selectin"`) so accessing them from a template is safe.

## When a new kind ships

1. Add the per-kind form-body partial `posts/_<kind>_form.html` (a `{% macro %}` taking `(hx_method, action, submit_label, post=None)`) using the shared field-render macros in [`../_shared/form_fields.html`](../_shared/form_fields.html).
2. Add `posts/new_<kind>.html` and `posts/edit_<kind>.html` as ~5-line wrappers around the form macro. Register their paths on the kind's `PostKindSpec` in [`src/domain/models/posts/post_kinds.py`](../../models/posts/post_kinds.py); the route layer reads `spec.create_template` / `spec.edit_template` from there.
3. Add a `{% elif post.kind == "<kind>" %}` branch in `_item.html` (`post_item`: pick the per-kind detail relationship, the lead text, the kind glyph icon name, and the meta-line composition) and `detail.html` (full read-view body — header, description, match-facts `<dl>`, optional call-to-action footer). If "Seeking"/"Providing" labels don't fit the new kind, extend the `choices=` tuple on `ChoiceFilter("kind", ...)` in [`src/domain/specs/post.py`](../../specs/post.py). Add an `<a href="/posts/form?kind=<new>" role="button">…</a>` entry to `form_new.html` so the kind picker offers it. The kind `<select>` option in the toolbar filter follows automatically from the spec-declared filter choices.
4. If the kind introduces a new controlled-vocabulary, add the tuple, the `*_LABELS` dict, **and** the `*_ICONS` dict (Lucide icon names) to `src/domain/models/enums.py` and register all three as Jinja globals in `src/framework/rendering/templating.py`. The shared `select_field` macro renders dropdowns from the labels; the listing-row macro uses the icons. The `test_icons_cover_their_tuples` guard in `test_schema.py` fails the build if an icon entry is missing.
