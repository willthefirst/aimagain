# Posts templates

Jinja templates for the post CRUD flows. HTMX-driven; forms submit form-encoded data via `hx-{post,patch}` (see [`_client_referral_form.html`](_client_referral_form.html) / [`_provider_availability_form.html`](_provider_availability_form.html)). Multi-checkbox fields (`desired_times`, `services`, `settings`) are normalized on the wire schema by `_scalar_to_list` in [`src/domain/logic/posts/schema.py`](../../logic/posts/schema.py).

## Files

- `list.html` — listing page (`GET /posts`). Renders a `<ul id="posts-list">` via the `post_item` macro in `_item.html` — one `<li>` per post, no custom CSS. The list uses Pico's default `<ul>` styling (bullets + indent); the row markup itself is pure semantic HTML with no classes. The toolbar (rendered by `views/list.html` → `_shared/_toolbar.html::page_toolbar`) carries the search link on the left and a "Create post" `<a role="button">` on the right (linking to `/posts/form` (no `?kind=`), which renders the kind picker). The search link reads "Search posts" when no filters are applied; with filters active it summarizes them inline ("Type: Seeking, Description: needle, +1 more filter") and gets a sibling "Clear all" link. Every filter control — `?kind=` (Seeking / Providing), `?q=`, `?posted_by=`, `?state=`, `?city=`, `?age_group=`, `?language=` — lives on `/posts/search` (rendered by `views/search.html`). `?kind=` is rejected with 422 on unknown via `ChoiceFilter.value_type=Literal[...]`. Filters left out today: `created_at` (waits on a `DateRangeFilter` type) and `insurance` (vocab asymmetric across kinds — needs a unified posture mapping). The `#posts-list > li` selector wraps each row; each carries `data-row-id` and `data-kind` for tests.
- `search.html` — the dedicated filter page (`GET /posts/search`). One-line stub that extends `views/search.html` and sets the `Posts` breadcrumb label; every form control is driven by `POST_ENTITY.declared_filters`. Submits via GET back to `/posts`; the search page never owns applied state — it constructs a URL the list page reads.
- `_item.html` — `post_item(post, active_kind=None)`. Renders a two-line `<li>` for the listings feed. Title line: `<small>May 15</small> <mark data-kind-chip="…">Seeking</mark> <a>lead text</a>` — the date via the `format_post_date` Jinja filter (see [`src/framework/rendering/templating.py`](../../../framework/rendering/templating.py)), the standardized verb (`Seeking` for `client_referral`, `Providing` for `provider_availability`), and a single link whose text is the *lead*. Metadata line: a nested `<ul>` of `<li>` chunks (location, in-person/virtual format, age groups, languages when non-default, insurance posture) — the inline-list pattern. Each fact is its own `<li>`, and CSS in `base.html` styles the nested list (`#posts-list > li > ul`) inline with a `·` visual separator inserted via `::before`. The `·` lives in CSS rather than the markup, so the HTML stays clean and tools that read the DOM see structured chunks. **Lead text per kind:** `client_referral` → the description (truncated to 160 chars), or `"Seeking in <city>, <state>"` if description is empty. `provider_availability` → `<strong>{practice_name}</strong>` plus an em-dash + description (truncated to 120 chars) if one exists. Languages tokens are omitted when the post is English-only since that's the default. The kind chip is hidden when `active_kind is not None` (a single kind is selected) — it would be constant for every row; tests assert presence/absence via the `[data-kind-chip]` attribute. **No owner-username** in the row — the author appears on the detail page; the listing reads as Craigslist, not as a feed of posts-by-people.
- `detail.html` — single-post read view (`GET /posts/{id}`). The *unfold* of a listing row: sections are ordered by what a reader needs to decide whether to act. (1) `<header><hgroup>` echoes the row's chip + a kind-appropriate title (synthesized `"Seeking in <city>, <state>"` for client_referral; `practice_name` for provider_availability). (2) Description prose, promoted above the metadata grid. (3) Match-facts `<dl>` — the row's meta-line tokens expanded into full lists (every age group, every language, every in-network carrier, schedule_text, treatment modality, sliding scale, cost). (4) Call-to-action `<section>How to refer</section>` for `provider_availability` carrying website + referral instructions. Posted-at uses the same `format_post_date` filter as the list. Includes `_owner_actions.html` in the footer.
- `_client_referral_form.html` / `_provider_availability_form.html` — per-kind form-body macros. Each takes `(hx_method, action, submit_label, post=None)` and renders the full intake form using the shared field-render macros from [`../_shared/form_fields.html`](../_shared/form_fields.html). Field order, section grouping, labels, and required/optional state live here in one place per kind.
- `new_<kind>.html` — create-form page; ~5-line wrapper that imports the per-kind form macro and calls it with `hx_method="post"`, `action="/posts"`.
- `edit_<kind>.html` — edit-form page; same wrapper pattern with `hx_method="patch"`, `action="/posts/{id}"`, and `post=post` for prefill.
- `_owner_actions.html` — partial showing Edit/Delete actions for owners and admins; kind-agnostic.

## Parent / per-kind detail

`Post` is split into a parent row (id, kind, owner, timestamps) and a per-kind detail row. Kinds today: `client_referral` (`post.client_referral_detail`) and `provider_availability` (`post.provider_availability_detail`). Both carry the scalar (single-value) fields from their intake forms plus the `desired_times` (7×3 grid) and `services` (5-checkbox) multi-selects, both stored as JSON. CR's `services` is optional; PA's is required-min-1. PA also carries the `settings` (5-checkbox) multi-select (required-min-1).

Templates dereference through the right relationship per branch: `{{ d.description }}` after `{% set d = post.client_referral_detail %}` inside a `kind == "client_referral"` block, etc. Don't reach for `post.title` — it isn't there. Detail relationships are eager-loaded (`lazy="selectin"`) so accessing them from a template is safe.

## When a new kind ships

1. Add the per-kind form-body partial `posts/_<kind>_form.html` (a `{% macro %}` taking `(hx_method, action, submit_label, post=None)`) using the shared field-render macros in [`../_shared/form_fields.html`](../_shared/form_fields.html).
2. Add `posts/new_<kind>.html` and `posts/edit_<kind>.html` as ~5-line wrappers around the form macro. Register their paths on the kind's `PostKindSpec` in [`src/domain/models/posts/post_kinds.py`](../../models/posts/post_kinds.py); the route layer reads `spec.create_template` / `spec.edit_template` from there.
3. Add a `{% elif post.kind == "<kind>" %}` branch in `_item.html` (`post_item`: pick the per-kind detail relationship, the lead text, the kind label, and the meta-line composition) and `detail.html` (full read-view body — header, description, match-facts `<dl>`, optional call-to-action footer). If "Seeking"/"Providing" labels don't fit the new kind, extend the `choices=` tuple on `ChoiceFilter("kind", ...)` in [`src/domain/specs/post.py`](../../specs/post.py). Add an `<a href="/posts/form?kind=<new>" role="button">…</a>` entry to `form_new.html` so the kind picker offers it. The kind `<select>` option in the toolbar filter follows automatically from the spec-declared filter choices.
4. If the kind introduces a new controlled-vocabulary, add the tuple + `*_LABELS` dict to `src/domain/models/enums.py` and register both as Jinja globals in `src/framework/rendering/templating.py`. The shared `select_field` macro then renders dropdowns from them with no further per-template work.
