# Posts templates

Jinja templates for the post CRUD flows. HTMX-driven; forms submit form-encoded data via `hx-{post,patch}` (see [`_client_referral_form.html`](_client_referral_form.html) / [`_provider_availability_form.html`](_provider_availability_form.html)). Multi-checkbox fields (`desired_times`, `services`, `settings`) are normalized on the wire schema by `_scalar_to_list` in [`src/domain/logic/posts/schema.py`](../../logic/posts/schema.py).

## Files

- `list.html` — listing page (`GET /posts`). Renders a stack of Pico `<article>` cards inside `<section id="posts-list">` via the `post_card` macro in `_card.html` — not the shared `index_table` macro, because the polymorphic kinds need an information hierarchy (kind chip, synthesized title, meta line, description preview) that a table can't express. The shared `_shared/index_filters.html` macro renders the filter form above the list; controls come from `POST_ENTITY.filters` (a tuple of `Filter` instances — see [`src/framework/dispatch/filters.py`](../../../framework/dispatch/filters.py)) and a normal `<form method="get">` Apply round-trips the page. The page lands minimal: only filters with a URL-active value render visible; the rest stay `hidden` behind an "Add filter" picker (see `_shared/index_filters.html`). Available filters: `?kind=` (single `<select>`, 422s on an unknown value via `ChoiceFilter.value_type=Literal[...]`), `?q=` (description ILIKE over both detail tables), `?posted_by=` (owner-username ILIKE), `?state=` (multi-`<select>` over US states, ORed across `client_referral_detail.location_state` and the offering side's `Provider.location_state`), `?city=` (location_city ILIKE on the same two paths), `?age_group=` (multi-`<select>`, JSON-contains on both detail tables' `age_groups`), `?language=` (same JSON-contains pattern on `languages`). Filters left out today: `created_at` (waits on a `DateRangeFilter` type) and `insurance` (vocab asymmetric across kinds — needs a unified posture mapping). The `#posts-list article` selector wraps each card; each carries `data-row-id` and `data-kind` for tests. The "New X" links at the top are rendered from `post_kinds` (a list of `PostKindSpec`, passed in by `POST_ENTITY.static_context`).
- `_card.html` — `post_card(post, active_kind=None)`. Renders a Pico `<article>` (Pico v2's stock card primitive — no custom CSS). `<header><hgroup>` carries the kind chip (`<mark data-kind-chip="…">Seeking</mark>` / `Offering`), the synthesized title as an `<h3><a>` linking to the detail page, and a `<small>` posted-by/posted-at line. A `<small>` meta line summarizes the match axes joined by `·`: location, in-person/virtual format, two age-group labels (`+N` overflow), two language labels (`+N` overflow), insurance posture. A description preview (`truncate(200)`) closes the card. The kind chip is hidden when `active_kind is not None` (a single kind is selected) — it would be constant for every card; tests assert presence/absence via the `[data-kind-chip]` attribute. Title synthesis: `client_referral` → `"Seeking in <city>, <state>"`; `provider_availability` → the linked provider's `practice_name`. Branches on `post.kind` for which detail relationship + which provider lookup to read.
- `detail.html` — single-post read view (`GET /posts/{id}`). The *unfold* of a card: sections are ordered by what a reader needs to decide whether to act. (1) `<header><hgroup>` echoes the card's chip + title so the summary→detail relationship is visible. (2) Description prose, promoted above the metadata grid. (3) Match-facts `<dl>` — the card's chip-line tokens expanded into full lists (every age group, every language, every in-network carrier, schedule_text, treatment modality, sliding scale, cost). (4) Call-to-action `<section>How to refer</section>` for `provider_availability` carrying website + referral instructions. Includes `_owner_actions.html` in the footer.
- `_client_referral_form.html` / `_provider_availability_form.html` — per-kind form-body macros. Each takes `(hx_method, action, submit_label, post=None)` and renders the full intake form using the shared field-render macros from [`../_shared/form_fields.html`](../_shared/form_fields.html). Field order, section grouping, labels, and required/optional state live here in one place per kind.
- `new_<kind>.html` — create-form page; ~5-line wrapper that imports the per-kind form macro and calls it with `hx_method="post"`, `action="/posts"`.
- `edit_<kind>.html` — edit-form page; same wrapper pattern with `hx_method="patch"`, `action="/posts/{id}"`, and `post=post` for prefill.
- `_owner_actions.html` — partial showing Edit/Delete actions for owners and admins; kind-agnostic.

## Parent / per-kind detail

`Post` is split into a parent row (id, kind, owner, timestamps) and a per-kind detail row. Kinds today: `client_referral` (`post.client_referral_detail`) and `provider_availability` (`post.provider_availability_detail`). Both carry the scalar (single-value) fields from their intake forms plus the `desired_times` (7×3 grid) and `services` (5-checkbox) multi-selects, both stored as JSON. CR's `services` is optional; PA's is required-min-1. PA also carries the `settings` (5-checkbox) multi-select (required-min-1).

Templates dereference through the right relationship per branch: `{{ d.description }}` after `{% set d = post.client_referral_detail %}` inside a `kind == "client_referral"` block, etc. Don't reach for `post.title` — it isn't there. Detail relationships are eager-loaded (`lazy="selectin"`) so accessing them from a template is safe.

## When a new kind ships

1. Add the per-kind form-body partial `posts/_<kind>_form.html` (a `{% macro %}` taking `(hx_method, action, submit_label, post=None)`) using the shared field-render macros in [`../_shared/form_fields.html`](../_shared/form_fields.html).
2. Add `posts/new_<kind>.html` and `posts/edit_<kind>.html` as ~5-line wrappers around the form macro. Register their paths on the kind's `PostKindSpec` in [`src/domain/models/posts/post_kinds.py`](../../models/posts/post_kinds.py); the route layer reads `spec.create_template` / `spec.edit_template` from there.
3. Add a `{% elif post.kind == "<kind>" %}` branch in `_card.html` (`post_card`: pick the per-kind detail relationship, the synthesized title, the kind label, and the meta-line composition) and `detail.html` (full read-view body — header, description, match-facts `<dl>`, optional call-to-action footer). If "Seeking"/"Offering" labels don't fit the new kind, extend the `choices=` tuple on `ChoiceFilter("kind", ...)` in [`src/domain/specs/post.py`](../../specs/post.py). The "New X" link in `list.html` and the kind `<select>` option both follow automatically via the registry-driven loop and the spec-declared filter choices.
4. If the kind introduces a new controlled-vocabulary, add the tuple + `*_LABELS` dict to `src/domain/models/enums.py` and register both as Jinja globals in `src/framework/rendering/templating.py`. The shared `select_field` macro then renders dropdowns from them with no further per-template work.
