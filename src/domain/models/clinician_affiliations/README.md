# Affiliations cluster

The clinician's role at one organization — the steady-state context that varies per (clinician × org): location, insurance posture, sliding-scale flag, and how to refer.

`ClinicianAffiliation` was carved out of the former `providers` table over the multi-PR `Provider → Clinician + ClinicianAffiliation` split (issues #629 and #635). After #642 PR 1, `affiliations.clinician_id` is the canonical owner FK, and a clinician may carry multiple affiliations (1:N). See [`../clinicians/README.md`](../clinicians/README.md) for the person side.

## Files

- `clinician_affiliation.py` — `ClinicianAffiliation`. Holds the steady-state **context** for one (clinician × org) — everything that doesn't vary per announcement: location (`location_city`, `location_state`, declared **inline** as nullable `Text`, no `LocationMixin` and **no ZIP** — `location_city` is a city or practice area, like a referral), the insurance posture (`accepts_out_of_network`, `in_network_carriers`, `sliding_scale`), how to refer (`website`, `referral_instructions`), and the denormalized `currently_accepting_new_patients` cache — see "Steady-state context" below. FKs: `clinician_id` (RESTRICT) is the person; `org_id` (RESTRICT, **nullable**) is the organization. The relationship is 1:N — one clinician may carry multiple affiliations. `(clinician_id, org_id)` is not UNIQUE: one clinician can hold multiple affiliations at the same org with different attributes (different location / insurance posture), and the curation rule belongs in business logic, not the schema.
- `test_affiliation.py` — model-layer regression coverage (multi-affiliation support, per-role writes, persists-via-cascade).

## The "every clinician has ≥1 affiliation" invariant

A `ClinicianAffiliation` is the **context container**: it owns location, insurance posture, and how-to-refer instructions. That context genuinely varies per (clinician × context) — the same person can work as a cash-pay clinician in private practice AND as an Aetna-paneled clinician at a group, both at once. So `ClinicianAffiliation` is the unit those vary on, not `Clinician`. (Per-announcement dimensions — services, session format, cohort, cost — vary even more finely, so they live on the opening post; see "Steady-state context" below.)

That means every clinician — including a solo practitioner with no LLC and no group — has at least one affiliation. The "solo" case is a `ClinicianAffiliation` row with `org_id IS NULL`: the row carries the context; the absence of an `Organization` reflects that there is no separate legal/branding entity. The `Clinician` proxy properties (`clinician.location_city`, `.accepts_out_of_network`, etc.) read from / write to this single affiliation; per [`../clinicians/README.md#per-affiliation-proxy-setters-require-a-primary-affiliation`](../clinicians/README.md#per-affiliation-proxy-setters-require-a-primary-affiliation), the setters raise if no affiliation exists.

Location columns (`location_city`, `location_state`) are nullable: a stub affiliation auto-created at NPI verify time hasn't yet been asked those questions; NULL means "unset." The auto-create lives in `after_create_clinician_verification` ([`../../logic/clinicians/handlers.py`](../../logic/clinicians/handlers.py)) — the canonical "this clinician is real and going to stick around" moment. The backfill migration `9501786659b3` covers pre-existing solo clinicians.

## Steady-state context

The affiliation is the durable-entity side of the [steady-state split](../README.md#steady-state-context-vs-per-announcement-dimensions): it holds only what doesn't change announcement-to-announcement for one (clinician × org) — location (`location_city` / `location_state`), insurance posture (`accepts_out_of_network` / `in_network_carriers` / `sliding_scale`), how to refer (`website` / `referral_instructions`), and the denormalized `currently_accepting_new_patients` cache.

The remodel **reversed** the #1358 PR-f "steady-state profile on affiliation" split for the per-announcement dimensions. The service lines / delivery format / cohort served / cost are *not* properties of the affiliation — a clinician can post two openings under the same affiliation targeting different cohorts or formats — so they live on the opening post (`OpeningDetail`), which is now self-describing. See [`../posts/README.md`](../posts/README.md) for the current `OpeningDetail` shape (it carries its own `session_format` / `services` / `services_other_text` / `age_groups` / `genders` / `cost` on the `ReferralService` vocabulary). The affiliation no longer carries `services` / `settings` / `modalities` / `age_groups` / `genders` / `cost`, and no longer carries the session-availability columns.

`languages` lives on `Clinician` (a person attribute, invariant across affiliations), not on the affiliation. See [`../clinicians/README.md`](../clinicians/README.md).

`currently_accepting_new_patients` is a denormalized cache toggled by the `OpeningDetail` lifecycle. Distinct from the analogous flag on `Program.accepting_referrals` which is an operator-set standing posture. The wire surface (`src/domain/logic/clinician_affiliations/schema.py`) exposes the steady-state context fields on `ClinicianAffiliationCreate` / `ClinicianAffiliationUpdate` / `ClinicianAffiliationRead`; `currently_accepting_new_patients` is `Read`-only — server-managed, never accepted on the wire.

## Write path: how a clinician edit lands on ClinicianAffiliation

After #1308, the affiliation's context is patched **directly on the affiliation**, not through the clinician's PATCH form: `ClinicianUpdate` is **person-level only** (identity + person-level claims like `affirming_identities`, `clinical_niches`, `languages`), and the affiliation owns the per-(clinician × org) steady-state context. After the canonical-pattern conversion (#1402), each affiliation has its own list / new / edit pages under `/clinicians/{clinician_id}/clinician_affiliations[/...]`; the edit form surfaces the context cluster (org, location, in-network, OON, sliding-scale, `website` / `referral_instructions`) — i.e. every field on the wire schema's Update surface. The per-announcement dimensions (services, session format, cohort, cost) are edited on the opening post, not here. `currently_accepting_new_patients` is not editable from the form: it's the server-managed cache (toggled by the OpeningDetail lifecycle), surfaced read-only on the list page as an "Accepting new patients" badge.

- **Create clinician**: the framework's generic create handler calls `Clinician(**payload.model_dump())`. If per-role kwargs are supplied (older code paths / tests), they are forwarded into a new `ClinicianAffiliation` appended onto `clinician.clinician_affiliations`; otherwise the verification handler creates a stub with all per-role columns NULL/default. `cascade="all, delete-orphan"` flushes both rows together.
- **Patch a ClinicianAffiliation's posture**: `PATCH /clinicians/{id}/clinician_affiliations/{aff_id}` with the per-role fields. Mounted via the framework's generic sub-resource update handler against `ClinicianAffiliationUpdate`. This is the canonical write path for posture after #1308.
- **Add a second ClinicianAffiliation**: `POST /clinicians/{id}/clinician_affiliations`. `ClinicianAffiliationCreate` is fully optional after PR-7, so the inline "Add another practice" form on the clinician edit page can create a solo (no-org) row by leaving the org dropdown on its "(Solo practice — no organization)" option. The framework constructs `ClinicianAffiliation(**payload.model_dump())`; the new row sits alongside the existing one(s).
- **Remove an ClinicianAffiliation**: `DELETE /clinicians/{id}/clinician_affiliations/{aff_id}` removes the row through the framework's generic delete handler.

## Read path: one join, two doors

The `(clinician × org)` join is read from **both** ends. The clinician edit page lists a clinician's affiliations by `clinician_id` (the canonical owner FK, see above). The org page lists the same rows by `org_id` as the org's **Members** — `GET /organizations/{id}/members` (the I6 org-profile redesign, #1524). Same join, two doors: one keyed on the person, one on the org.

Both doors are *read* surfaces on the org side: mutation (add / edit / remove) only happens through the clinician-side routes above, because the affiliation is FK-owned by the clinician (`clinician_id` RESTRICT). The org Members list therefore links each row to the clinician's own affiliation edit page rather than mounting org-side mutation routes — there is no org-keyed write path, and adding one would duplicate the authz surface for no new capability. The org-side list query is `ClinicianAffiliationRepository.list_org_members(org_id)` ([`../../logic/clinician_affiliations/repository.py`](../../logic/clinician_affiliations/repository.py)); it mounts as a `RelatedListSubresource` on `ORGANIZATION_ENTITY` (handler `handle_list_org_members` in [`../../logic/organizations/handlers.py`](../../logic/organizations/handlers.py)). Org-side URL grammar follows the owner-scoped 1:N pattern in [`../../routes/RESOURCE_GRAMMAR.md`](../../routes/RESOURCE_GRAMMAR.md).
