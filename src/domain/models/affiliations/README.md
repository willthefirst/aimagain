# Affiliations cluster

The clinician's role at one organization — practice-role attributes that vary per (clinician × org): insurance posture, sliding-scale flag, cost, location, modality.

`Affiliation` was carved out of [`../providers/provider.py`](../providers/provider.py) over the multi-PR `Provider → Clinician + Affiliation` split (issues #629 and #635). #629 PR 2 added the table and backfilled one row per `Provider`. #629 PR 3 switched the directory's read path onto `provider.affiliation.*` ([`../../logic/providers/view.py`](../../logic/providers/view.py)). **#635 PR B made `affiliations` the single source of truth** by dropping the duplicated per-role columns from `providers` and rewriting `Provider.X` as `@property` proxies. **#642 PR 1 makes Provider → Affiliation 1:N** by dropping the UNIQUE on `affiliations.provider_id` and surfacing the rows as an inline list on the clinician edit page (same UX as licensures). **#642 PR 2 made the provider detail page render one stacked `entity-card` per affiliation** (heading "At <Org>" linking to the owning Organization; per-affiliation address, sessions, insurance, sliding scale, cost). Person-level data (the clinician name in the top header, plus the licensures / educations / certifications below) renders once, not per-affiliation — credentials FK to `clinicians.id` after #635 PR A. The view-model helper `affiliation_card_view(aff, org)` in [`../../logic/providers/view.py`](../../logic/providers/view.py) emits the per-affiliation dict shape; `provider_card_view(provider)` exposes the list as `view.affiliations`. The flat per-role keys on `provider_card_view` still read off `provider.primary_affiliation` so the directory listing and the post-opening dropdown keep working unchanged — #642 PR 3 collapses the listing to one row per Clinician.

See [`../clinicians/README.md`](../clinicians/README.md) for the person side and [`../providers/README.md`](../providers/README.md) for the structural-only cluster the split came out of.

## Files

- `affiliation.py` — `Affiliation`. Holds the per-role columns: `(location_city, location_state, location_zip)` via `LocationMixin`, `in_person_sessions`, `virtual_sessions`, `accepts_out_of_network`, `in_network_carriers`, `sliding_scale`, `cost`. FKs: `clinician_id` (RESTRICT) is the person; `org_id` (RESTRICT) is the organization; `provider_id` (CASCADE, **not UNIQUE** after #642 PR 1) links back to the owning `providers` row. The relationship is 1:N — a Provider may carry multiple Affiliations; reads that still need to dereference "the" affiliation per row go through `Provider.primary_affiliation`, which picks the oldest by `created_at`. A module-level SQLAlchemy event listener (`_inherit_clinician_id_from_provider`) defaults `affiliation.clinician_id` from the parent provider's clinician when an `Affiliation` is appended into `Provider.affiliations`, so the `POST /clinicians/{id}/affiliations` wire payload doesn't have to carry the FK. `(clinician_id, org_id)` is not UNIQUE either: one clinician can hold multiple affiliations at the same org with different attributes (different rate / schedule / location), and the curation rule belongs in business logic, not the schema.
- `test_affiliation.py` — model-layer regression coverage (auto-create-on-Provider-init, skip-when-supplied, per-role writes land on the primary affiliation via the `Provider` property setters, persists-via-cascade, multi-affiliation support, `primary_affiliation` picks the oldest by `created_at`).

## Write path: how a Provider edit lands on Affiliation

- **Create Provider**: the framework's generic create handler calls `Provider(**payload.model_dump())`. `Provider.__init__` peels the per-role kwargs (`org_id`, `location_*`, sessions, insurance posture, `sliding_scale`, `cost`) off `kwargs` and forwards them into a transient `Affiliation` appended onto `provider.affiliations` (the singleton "primary" affiliation for the new Provider). `cascade="all, delete-orphan"` on the relationship flushes both rows together.
- **Update primary affiliation via Provider PATCH**: `repo.patch(provider, location_city="X")` calls `setattr(provider, "location_city", "X")`, which hits the `@property` setter on the `Provider` class and writes through to `provider.primary_affiliation.location_city`. No mirror listener required — there's only one place the value lives.
- **Add a second Affiliation**: `POST /clinicians/{id}/affiliations` with the per-role fields. The framework constructs `Affiliation(**payload.model_dump())` and appends it onto `parent.affiliations`; the SQLAlchemy event listener fills `clinician_id` from the parent. The new row sits alongside the existing one(s); reads that dereference `primary_affiliation` still pick the oldest.
- **Remove an Affiliation**: `DELETE /clinicians/{id}/affiliations/{aff_id}` removes the row through the framework's generic delete handler. Deleting the last Affiliation leaves the Provider with `primary_affiliation == None`; the per-role property proxies return `None` for every field. PR 3 (this issue) rolls the listing up by Clinician so a no-affiliations Provider drops off the list.
